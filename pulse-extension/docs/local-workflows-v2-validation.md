## Scoped-review v2 implementation — historical validation checkpoint

Review now has an explicit, immutable `static`, `build-tests`, or `ui-e2e` scope. The website presents one entry with visible presets and a `build-tests` initial default, while model/effort choices remain separate. Presets are not cumulative quality levels: runtime verification uses necessary builds/tests rather than requiring every earlier test. Static review does not execute builds/tests/UI, and unselected coverage is not failed execution.

Structured results separate workflow completion, code-review conclusion, product assessment, attributed verification evidence and an optional focused verification recommendation. Ordinary GitHub proposals remain subject to the usual account, SHA, finding, evidence and confirmation checks. The previously introduced fixed `request-evidence` / `approve-with-limitations` choices are superseded; `reviewDecisionId` is not a submit bypass.

Supplemental verification is created through internal `reviews.verify`, tied to the exact parent result, recommendation and original revision. Missing or unknown environment readiness needs explicit prerequisite confirmation, followed by child setup checks. Host-owned boundary snapshots distinguish original-PR source from local candidates or unknown provenance; they are not continuous proof that source never changed during execution. `reviews.related` shows compatible evidence and a current conclusion without rewriting the original report or automatically creating/submitting a GitHub action.

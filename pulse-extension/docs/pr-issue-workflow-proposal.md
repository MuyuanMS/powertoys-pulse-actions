# PR 与 Issue 工作流方案（已实现并完成本地验证）

日期：2026-09-15。

本文是确认并实现的需求基线。实现采用 v3 结果合同，具体字段与接口见 [workflow-v3-wire.md](workflow-v3-wire.md)，本地验证与限制见 [workflow-v3-validation.md](workflow-v3-validation.md)。插件代码及 prompt 优化已以 `b33319c` 合入并推送插件 `main`；网站接入改动按用户要求保留在工作分支。完整真实模型任务与 GitHub 写入验收尚未执行，用户将稍后测试；CI 暂不在本阶段范围内。最新交付状态见 [acceptance.md](acceptance.md)。

## 1. 总体原则

1. Agent 完成调查、分析与复核，统一交付结构化最终结果。插件不从自由文本中猜测状态、按钮或执行命令。
2. 最终结论、默认建议、用户选择的动作分别保存和展示。默认建议用于选择初始动作、预填内容，不是执行授权。
3. GitHub 操作区固定存在，不依赖模型是否返回对应 `nextActions`。AI 提案是内容来源和建议，用户仍能主动选择操作。
4. GitHub 写入由插件展示目标与具体内容，用户确认后交给 Host 执行。分析和本地实现任务不直接发布评论、审批、关闭或合并。
5. 同一次 PR 审查固定到一个 PR SHA。原 PR、本地修改版以及不同版本的证据分别记录，不能混用。
6. 任务执行状态、分析完成情况、产品或验证结果分开。完整的调查可以发现缺陷；未做范围外的测试不意味着本次分析失败。
7. 继续支持不同 CLI；默认和单次 CLI、模型、推理强度设置保留。业务 prompt 由插件仓库维护，不依赖 Copilot 云端 Review 或某个特定 Agent。

## 2. PR：执行范围与 Loop

保留一个 Review 入口和三个执行范围，默认选项继续为编译与自动化测试，允许记忆用户选择：

| 范围 | 本次执行内容 |
| --- | --- |
| 静态代码审查 | 检查代码、上下文、现有测试及已有证据；不执行构建、测试或实际 UI 操作 |
| 编译与自动化测试 | 代码审查，加相关构建和自动化测试；不操作实际应用 UI |
| UI／E2E 场景验证 | 代码审查，加相关运行场景；只执行必要的构建和测试，不机械重复整个仓库的检查 |

静态审查必须采用内部 Loop，向用户一次性交付最终报告。其他包含代码审查的范围复用同一审查和复核逻辑。

流程：完整检查当前 PR 差异及受影响路径 → 汇总问题与疑点 → 逐条复核 → 补查遗漏 → 收敛 → 发布最终报告。

- 不设置 Top N，不因为已经发现几个问题或发现 P0/P1 就提前结束。
- 每条候选问题都检查真实性、当前版本是否仍存在、影响、根因和修复建议；合并重复项，剔除误报。
- 补查发现新的有效问题后，继续复核相关问题和受影响路径。
- 收敛要求：选定范围的检查已完成；所有最终问题已复核；补查未再产生待复核的新问题；覆盖范围和剩余验证限制已记录。
- 当前可完成的检查在本轮完成；未选择的 UI/E2E 不因 Loop 自动变为本次必做项。
- 运行中只显示阶段进度，不逐条发布临时发现或中间轮次。完成后一次性呈现全量最终列表；列表可分页，但不能省略或只保留前若干问题。
- 中断、资源限制或覆盖未完成时，明确显示“审查未完成”，不能把部分报告包装为完整最终结论。保留已有证据和日志。
- “完整审查”要求完整覆盖和报告，不承诺能够证明不存在任何潜在遗漏，也不要求无限循环。

## 3. PR：最终问题结构

每个最终问题包含：

| 字段 | 内容 |
| --- | --- |
| 稳定问题 ID | 用于勾选、编辑、评论关联及重试恢复 |
| priority | `P0`、`P1`、`P2`、`P3` |
| title / description | 问题标题、具体表现 |
| location | 文件与相关代码位置；无法对应行内位置时为一般问题 |
| impact / trigger | 影响和触发条件 |
| rootCause | 根因解释及其依据；仍不确定的部分明确标注，不虚构确定性 |
| evidence | 可核查的代码、文档、测试或运行观察 |
| fixSuggestion | 具体修复建议及必要的注意事项 |
| feedback | 普通评论草稿；可准确表达代码替换时，另外提供代码 suggestion 及其有效位置 |

只有复核后成立的问题进入确认问题列表。待验证的推测放在验证限制或 E2E 建议中，不冒充已确认缺陷。已经有确凿缺陷证据时，根因尚有局部不确定不能成为隐藏该缺陷的理由；应准确说明证据边界。

## 4. PR：独立 E2E 验证建议

静态审查最终结果中固定展示“E2E 验证建议”卡片，显式给出以下三个等级之一：

| 等级 | 含义 |
| --- | --- |
| 不需要 | 静态分析和 UT 能覆盖改动的正确性，说明覆盖依据 |
| 建议 | 静态审查确信度不足，E2E 可以补充证据、消除疑点 |
| 必须 | 关键正确性需要实际运行场景证明，静态审查和 UT 无法替代 |

卡片包含：等级、理由、待验证的关键问题、具体场景、预期结果、前置条件、已有相关证据，以及运行或查看验证结果的入口。

- “不需要”也必须明确返回，不能把没有建议或旧数据缺字段解释为“不需要”。
- 等级表达 E2E 的必要性，不表示测试已经通过；UT 是否实际运行及结果也分别记录。
- “必须”影响审查建议，不新增 Approve 权限状态，也不把完成的静态审查改成失败。
- 条件具备时可启动关联验证；缺少条件时显示具体前提，避免把 Settings 或原样 Retry 当作通用解决办法。
- 追加验证继承原 Review 的问题、计划和 SHA，不重复完整代码审查，支持单次 CLI、模型和推理强度设置。
- 同版本、同原始代码的补充证据汇总展示，原报告保留。需要的验证已完成时，主入口改为查看结果；重复验证作为明确的次要选择。
- 后续验证不会把原来的必要性等级改写成另一等级；指定场景已充分覆盖并通过时，可以显示“必须（证据已补足）”，并更新当前建议。不能只因子任务退出码为零或其中一个检查通过就认定补足。实际失败、混合矛盾证据或仍无结论则如实显示。

## 5. PR：审查建议和 GitHub 操作

### 5.1 建议规则

| 当前情况 | 审查建议 |
| --- | --- |
| 当前版本存在已确认、仍未解决的 P0 | 优先处理阻塞问题 |
| 无 P0，但存在 P1 | 优先反馈和修复问题 |
| 无 P0/P1，但必须的 E2E 证据尚未补足 | 先补充 E2E，不推荐 Approve |
| 无 P0/P1，E2E 不需要或仅为建议 | 推荐 Approve；建议级 E2E 仍在独立卡片提示 |
| 必须的 E2E 已补足，且无 P0/P1 | 可以更新当前建议为 Approve，并保留原审查和验证历史 |
| 分析未完成或没有有效最终报告 | 不伪造正面审查结论，显示未完成原因和已有事实 |

P1 与必须的 E2E 可以同时存在：主建议优先反馈问题，E2E 卡片仍完整保留，不因主建议而丢失另一类要求。

### 5.2 操作权限

- GitHub 操作区始终存在。Approve、普通评论、带代码建议的评论、Request changes、关闭、合并及适用 CI 操作不依赖 AI 提案才出现。
- 本轮确定的 Approve 业务限制只有：当前原始 PR 版本存在已确认、未解决的 P0。
- P1/P2/P3、未做 UI、E2E 为必须、调查未完成、CLI 失败或没有 AI 审批提案，不额外构成插件禁止用户 Approve 的业务理由。
- 没有确认的 P0 不代表 Agent 已证明没有 P0；尚未完成的分析仍必须如实展示，不能产生虚假的“审查通过”文案。
- 账号权限、当前 PR 状态、目标/SHA 校验、无法确定的上次提交结果等真实执行前提继续检查；这些不是新的 AI 审批结论。
- 其他 GitHub 操作也不因缺少模型提案而消失，按各自真实执行条件处理。不得通过旧的“所有检查通过/产品 assessment 必须 passed”字段暗中恢复对人工 Approve 的限制。
- 仅验证任务不生成虚假的完整代码审查结论；PR 目标页面的固定人工操作区仍按同一规则处理。

### 5.3 问题勾选和提交内容

- 默认勾选具有可用代码 suggestion 的已确认问题；用户可以取消、勾选其他问题或编辑草稿。
- 勾选带代码 suggestion 的问题，默认准备带代码建议的评论；其他问题准备普通评论。
- 混合勾选时，同时准备对应的代码建议和普通评论，不能夹带未选问题。
- 代码 suggestion 必须对应当前 PR 可用位置；不能准确定位或不适合代码替换的问题，使用普通评论。
- 在默认联动模式下，取消全部勾选时回到审查推荐的默认动作；例如只有 P2/P3 时总体仍可推荐 Approve。
- 用户可以主动改选 GitHub 动作；明确的用户选择优先于默认联动，刷新或后续勾选不能反复覆盖它。切换动作时保留已有勾选与编辑；确认页清楚显示最终选择的审查决定及将发送的内容，不能静默丢弃或附加内容。
- suggested changes 指评论里的代码 suggestion；GitHub 的 Request changes 是独立的审查决定，不因为勾选问题而自动提交该决定。

## 6. Issue：统一调研和交付

Issue 按 Feature Request 与 Bug 采用不同调研要求，类型可由系统建议并允许用户修正。类型与本次是否实施分开：调研结果可以推荐后续实现或修复，不自动开始完整开发。

两类结果均统一呈现“最终调研结论与依据/方案”以及“下一步建议与操作”。结果不拆成一组互相竞争的判断卡片。调查能完成的工作先完成；后续任务继承已保存上下文和计划。

## 7. Feature Request

一次调研中一并完成：用户需求与场景、现有功能、重复需求或进行中的实现、当前代码/架构/平台能力、限制、实现方案与验收条件。

可行性属于整体研究的一部分。最终只给综合结论，不新增独立 feasibility 状态、流程或卡片。

| featureAssessment.status | 最终结果必须包含 | 插件默认建议 |
| --- | --- | --- |
| `ready` | 明确需求、可行依据、实施方案、验收标准 | 开始实现 |
| `needs_information` | 影响实施的具体缺失信息、为什么需要、询问正文 | 编辑并发送询问 |
| `needs_decision` | 待决定事项、可选方案及取舍 | 查看/选择方案，或发送讨论评论 |
| `already_supported` | 已有能力、适用条件、使用说明、证据 | 发送使用说明 |
| `duplicate` | 原始 Issue、重合点和差异、重复依据 | 提供 Close as duplicate，也可仅发送关联说明 |
| `not_feasible` | 在当前需求和平台约束下无法实现的原因、调研依据、关键限制、可选替代方案 | 发送解释与替代方案 |

`ready` 表示形成了明确、可行的实施方案，不代表维护者已经接受需求。调研证据不足或当前机器缺少工具/权限，不等于功能技术上不可实现；应如实报告限制或调研未完成。

## 8. Bug

Bug 调查必须内部 Loop：调查事实 → 验证假设 → 定位原因 → 逐条复核 → 补查相关遗漏 → 一次性交付。围绕当前 Issue 相关问题，不扩展成无边界的全仓库审查。

| bugAssessment.status | 最终结果必须包含 | 插件默认建议 |
| --- | --- | --- |
| `confirmed` | 缺陷证据、影响、优先级、根因及修复建议；已知限制 | 有明确可执行方案时开始修复，也可发送调查结论 |
| `needs_information` | 报告者掌握、现有材料无法取得的关键事实，以及具体问题 | 编辑并发送询问 |
| `needs_verification` | 已确认事实、待验证假设、具体实验/复现计划、预期观察、前置条件 | 运行复现/验证，或先准备必要条件 |
| `already_fixed` | 已有上游修复、相关 PR/提交/版本及判断依据 | 发送修复说明，提供关闭操作 |
| `duplicate` | 原始 Issue、相同问题的证据 | 提供 Close as duplicate，也可仅发送关联说明 |
| `not_a_bug` | 预期与实际行为、设计或配置依据、解决方式 | 发送解释说明，提供关闭操作 |

确认的问题复用 P0/P1/P2/P3、位置、触发条件、影响、根因、修复建议和证据结构。若问题成立但当前项目无法修复，综合结论说明原因、限制及规避方式，不机械推荐开始修复。

实际复现情况另有结构化记录，仍放在同一份最终报告中：`reproduced`、`not_reproduced`、`not_run`、`blocked`，并带测试版本、环境、步骤、预期和观察。

- 充分的代码证据可以确认缺陷，不强制所有 Bug 都先跑完整 UI 复现。
- 未复现不能直接推出 not_a_bug；确认缺陷、确认根因和实际复现分别以证据说明。
- 当前任务能够完成的验证应在 Loop 内完成，不能因为尚未测试就提前返回 needs_verification。
- needs_information 缺的是现有材料中没有、需要报告者提供的事实；先查清代码、附件和已有日志中能够取得的信息。
- needs_verification 缺的是关键假设的验证证据，且本轮受环境、设备或范围约束无法完成。必须给可执行计划和具体前提，不返回笼统 Retry。
- 两者同时存在时，优先补齐影响验证的关键信息，同时保留后续验证计划。

## 9. Duplicate 与关闭

Feature Request 与 Bug 共用 `close-as-duplicate` 操作。

结构化提案必须包含 `duplicateOf`（原始 Issue 的仓库、编号、链接）、重复依据和可编辑的关联/关闭说明。模型不能只返回 duplicate 标签而不给目标。

确认界面展示：当前 Issue、唯一原始 Issue、将发送的说明、将关闭当前 Issue 的效果。用户可以只发送关联说明而不关闭。

执行时保留明确的关联说明并关闭当前 Issue。原始 Issue 引用不能因编辑正文而被静默替换。重复点击、丢失响应或部分执行不能造成重复评论；关联说明成功而关闭失败时，展示实际完成情况并恢复剩余步骤。

普通关闭也需要明确理由。分析完成、复现完成或本地修复通过，不自动构成关闭依据。

## 10. 结果合同与插件衔接（实现约定）

实现使用 v3 结果合同；保留 v1/v2 读取，不重写旧记录。固定人工操作采用本轮的独立权限规则，不继承旧模型提案的完成状态门槛。

| 结果部分 | 职责 |
| --- | --- |
| 任务/报告元数据 | 任务种类、目标、分析版本、所选范围、执行状态、最终报告是否完成及覆盖情况 |
| PR 最终报告 | 已复核问题、审查结论、当前建议；不决定固定按钮是否存在 |
| PR E2E 评估 | `not_needed` / `recommended` / `required`，原因、场景、前提和证据引用；验证完成情况另行记录 |
| Feature 综合结论 | featureAssessment 六种最终结论及对应依据、方案或待决定事项；无独立 feasibility 状态 |
| Bug 综合结论 | bugAssessment 六种结论、问题明细和实际复现记录 |
| 证据/验证/产物 | 来源、版本、原 PR 或本地候选、实际执行与观察、报告和日志位置 |
| plans | 可引用的实施、修复、复现、验证计划；包含目标、步骤、验收标准、前置条件和来源 |
| nextActions | 带理由、正文或计划引用的建议，支持默认推荐标记；不新增另一套 recommendedAction 来源 |

每个建议引用存在于同一份最终结果中的问题、草稿或计划。Host 从保存的结果读取内容，不能接受客户端或模型静默替换目标、计划、源版本或权限。结构化计划用于后续 Agent 的任务上下文，不是由插件执行的任意命令。

| 操作 | 插件行为 | 对接情况 |
| --- | --- | --- |
| PR 固定人工操作 | 选择决定、勾选/编辑问题、确认目标和内容，按新 P0 规则提交 | 重构当前依赖 AI 提案/结果成功的路径 |
| `comment` | 打开预填正文的编辑和确认 | 复用现有执行能力 |
| `close` | 展示关闭理由并确认 | 复用现有执行能力 |
| `close-as-duplicate` | 确认原始 Issue、关联说明和关闭效果，记录复合操作进度 | 新增 |
| `start-task` | 引用已保存计划，启动对应后续任务，允许单次 CLI/模型/强度设置 | 新增结果到任务的通用衔接 |
| Feature 调研/实施 | 使用 Feature 专用 prompt 和验收要求，不套用 Bug 复现门槛 | 新增对应任务支持 |
| Bug 调查 | 使用上述 Loop、最终结论和证据要求 | 新增对应调查任务支持 |
| Bug 修复、复现 | 继承调查结果、方案和版本信息，执行对应本地工作 | 复用并升级现有工作流 |
| Issue 补充验证 | 按计划执行针对性的 UT/运行场景，报告实际结果 | 新增 Issue 目标的验证衔接 |
| PR 补充 E2E | 继承 Review 计划、SHA 和上下文；保持原审查历史 | 复用并升级当前关联验证 |
| `create-pr` | 展示目标分支、已验证源 SHA、标题和正文，确认后创建 | 复用当前能力；不隐含 commit/push |
| 查看结果/日志/改动 | 导向保存的证据和产物 | 复用现有能力 |

新的本地实现/修复结果分别说明：改了什么、本地验证到什么程度、是否已发布或进入上游。仅有本地改动时推荐检查改动和必要验证；已有可用远端分支且满足发布条件时可准备创建 PR。本方案不为 create-pr 暗中增加提交或推送本地代码的副作用。

不按旧 high/medium/low 等级自动推断 P0，也不把旧记录缺少 E2E 评估解释为不需要。旧报告保持原有含义，界面明确标注未记录的字段。

## 11. 验收标准

1. PR 中发现 P0/P1 后仍完成其余范围检查；最终列表包含全部已复核问题，无 Top N 截断或中间轮次混入。
2. 每个问题有优先级、影响、证据、根因与修复建议；待验证推测不能冒充已确认 P0。
3. 无 AI 提案、任务未完成、CLI 失败和 E2E 必须时，固定 PR 操作区仍存在；Approve 只增加已确认当前 P0 这一业务限制。
4. P1 存在时建议反馈问题但允许手工 Approve；P0 存在时 Approve 禁用。
5. 仅 P2/P3 时可以推荐 Approve；默认勾选代码建议会使当前默认提交变成评论，两者分别展示。
6. 混合选择准确生成代码 suggestion 和普通评论；取消选择不夹带该问题；Request changes 不被自动替代或误触发。
7. E2E 始终明确为三档之一；必须且未补足时不推荐 Approve，但不新增禁止状态。
8. 已完成的静态审查不因未执行范围外 E2E 显示为失败；实际未完成则不伪称完整报告。
9. 关联验证只合并正确版本和来源的证据，成功/失败都能更新当前提示；原报告不改写，完成后优先查看结果。
10. Feature 把需求与实现能力调研整合在同一最终结论中；不可实现有具体原因和依据，无独立可行性状态或卡片。
11. Feature 六种结论和 Bug 六种结论均能输出对应内容和可消费的操作建议。
12. Bug 的信息缺口与验证缺口有明确区别；可在本轮完成的验证不会被推给下一步；未复现不自动变成 not_a_bug。
13. 两类 duplicate 都能选择 Close as duplicate，并固定原始 Issue；仅评论、部分完成和未知结果均可正确处理。
14. 后续任务继承选中的方案和上下文；相同请求恢复不重复创建任务，修改参数必须使用新的明确请求。
15. 本地修复成功不自动关闭 Issue，不暗中执行 GitHub 写入或推送代码。
16. 新旧结果均可读取；历史数据、用户配置和已有任务保持不变。网站仍只在任务分支修改，不合并或推送网站 main。
